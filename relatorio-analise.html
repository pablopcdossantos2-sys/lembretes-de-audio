FALHA-01

Perfis noturnos ignorados em dias futuros além da data de hoje

✓ Resolvido Agendamento
📁 app/src/main/java/com/example/domain/scheduler/ScheduleCalculator.kt

A condição que verificava perfis noturnos estava ancorada em searchDate == now.toLocalDate(). Quando o agendador calculava getNextNTriggers para dias futuros (ex: madrugada de sábado após sexta-feira), os disparos da madrugada eram descartados. Além disso, o laço anterior podia avaliar disparos além da meia-noite antes do avanço do dia.

Solução Aplicada: A validação isYesterdayOvernightActive agora cobre qualquer data futura (searchDate.isAfter(now.toLocalDate())), e o laço interno impõe if (currentInstant.toLocalDate() != searchDate) continue, garantindo que cada dia receba exclusivamente seus horários correspondentes de forma sequencial e sem repetições.
✗ Antes (Trava restrita ao dia corrente)
if (
    profile.crossesMidnight &&
    searchDate == now.toLocalDate() &&
    now.toLocalTime().isBefore(profile.endTime)
) {
    windowStartDates.add(searchDate.minusDays(1))
}
✓ Depois (Generalizado para todas as datas futuras)
val isYesterdayOvernightActive = profile.crossesMidnight &&
    profile.daysOfWeek.contains(searchDate.minusDays(1).dayOfWeek) &&
    (searchDate.isAfter(now.toLocalDate()) || now.toLocalTime().isBefore(profile.endTime))

if (isYesterdayOvernightActive) {
    windowStartDates.add(searchDate.minusDays(1))
}
// No laço:
if (currentInstant.toLocalDate() != searchDate) {
    currentInstant = currentInstant.plusMinutes(stepMinutes)
    continue
}
FALHA-02

Backup JSON perdia os arquivos gravados ao exportar apenas o caminho textual

✓ Resolvido Backup
📁 app/src/main/java/com/example/data/backup/BackupManager.kt & BackupData.kt

Ao exportar o arquivo de configuração, apenas a URI textual era salva (ex: file:///data/user/0/.../rec_1.wav). Ao restaurar em outro smartphone, os arquivos físicos não existiam no disco e os áudios gravados ficavam inativos.

Solução Aplicada: Adicionado o campo audioBase64 nos DTOs de áudio e lembretes. Durante a exportação, arquivos locais de até 10MB têm seus bytes lidos e codificados em Base64. Na importação, os bytes são decodificados, salvos fisicamente em context.filesDir/audio_recordings e vinculados com isActive = true. Teste automatizado incluído em BackupManagerTest.
✗ Antes (Apenas URI textual no JSON)
put("id", audio.id)
put("uriString", audio.uriString)
// Arquivos físicos eram perdidos na troca de aparelho
✓ Depois (Dados binários embutidos e restaurados)
val base64Data = audioFilePath?.let { path ->
    val f = File(path)
    if (f.isFile && f.length() in 1..(10 * 1024 * 1024)) {
        Base64.encodeToString(f.readBytes(), Base64.NO_WRAP)
    } else null
}

📁 app/src/main/java/com/example/service/AudioReminderService.kt & BootAndAlarmReceiver.kt

Se o sistema caísse em alarme aproximado no Android 12+, a permissão de iniciar serviços em primeiro plano a partir de background não era concedida.

FALHA-04

Ciclo de vida do tipo mediaPlayback e conformidade com Android 14

✓ Resolvido Segundo Plano
📁 app/src/main/java/com/example/service/AudioReminderService.kt

O tipo FOREGROUND_SERVICE_TYPE_MEDIA_PLAYBACK no Android 14 exige correspondência com reproduções reais de áudio para evitar encerramento forçado por consumo de bateria.

FALHA-05

Ausência de tratamento no OnAudioFocusChangeListener durante a reprodução

✓ Resolvido Áudio
📁 app/src/main/java/com/example/player/AudioPlayerManager.kt

O listener de foco de áudio estava vazio ({ /* handle if needed */ }). Se o usuário recebesse uma chamada telefônica ou navegação GPS durante a fala de um lembrete, o som continuava tocando sem atenuação.

Solução Aplicada: Implementado listener robusto: em AUDIOFOCUS_LOSS o áudio é parado com liberação de recursos; em AUDIOFOCUS_LOSS_TRANSIENT a reprodução é pausada; em AUDIOFOCUS_LOSS_TRANSIENT_CAN_DUCK o volume é reduzido para 20%; e em AUDIOFOCUS_GAIN a reprodução é retomada restaurando o volume original.
✗ Antes (Listener vazio)
.setOnAudioFocusChangeListener { /* handle if needed */ }
✓ Depois (Tratamento completo de perda/ducking/retomada)
private val audioFocusChangeListener = OnAudioFocusChangeListener { change ->
    when (change) {
        AUDIOFOCUS_LOSS -> stop()
        AUDIOFOCUS_LOSS_TRANSIENT -> mediaPlayer?.pause()
        AUDIOFOCUS_LOSS_TRANSIENT_CAN_DUCK -> mediaPlayer?.setVolume(duckVol, duckVol)
        AUDIOFOCUS_GAIN -> {
            mediaPlayer?.setVolume(targetVol, targetVol)
            if (isPausedDueToFocus) mediaPlayer?.start()
        }
    }
}
FALHA-06

Ajuste forçado de volume físico em STREAM_ALARM mesmo com useAppVolumeOnly ativado

✓ Resolvido Áudio
📁 app/src/main/java/com/example/player/AudioPlayerManager.kt

O método prepareAudioVolume elevava o volume do stream de alarme do sistema operacional mesmo quando a opção useAppVolumeOnly estava marcada pelo usuário.

Solução Aplicada: Quando useAppVolumeOnly está ativo, a função retorna imediatamente sem desmutar ou chamar setStreamVolume nem para STREAM_MUSIC nem para STREAM_ALARM, respeitando estritamente o volume de software no player.
FALHA-07

Alta pressão no Garbage Collector (GC) e recomposição excessiva no gravador PCM

✓ Resolvido Desempenho
📁 app/src/main/java/com/example/util/AudioRecorderHelper.kt

Buffers de 512 shorts lidos a 44.1kHz disparavam a análise FFT mais de 86 vezes por segundo, gerando centenas de alocações de arrays por segundo e quedas de frame na interface.

Solução Aplicada: Inserido controle de taxa (throttle) em AudioRecorderHelper via SystemClock.uptimeMillis() >= 33L (~30 FPS). O áudio continua sendo gravado a 44.1kHz sem perda de uma única amostra, enquanto as transformações de visualização operam suavemente na taxa ideal do display.
FALHA-08

Inexistência de Migração Room Registrada para a Versão 2 (MIGRATION_1_2)

✓ Resolvido Backup
📁 app/src/main/java/com/example/data/db/AppDatabase.kt

O banco de dados declarava version = 2 sem registrar o objeto Migration(1, 2) no databaseBuilder, o que provocaria erro de inicialização caso o app fosse atualizado sobre uma base de versão 1.

Solução Aplicada: Criado e registrado val MIGRATION_1_2 = object : Migration(1, 2) com comandos SQL idempotentes para adição das colunas de fade-in e política de retomada. Adicionalmente, o DatabaseCallback foi corrigido para passar o contexto da aplicação, evitando race condition de inicialização.
FALHA-09

Abertura de streams com openInputStream no ContentResolver a cada emissão do Flow

✓ Resolvido Desempenho
📁 app/src/main/java/com/example/ui/viewmodel/MainViewModel.kt

Em audiosDomainFlow, cada arquivo importado com content:// abria um InputStream através de IPC com o provedor de conteúdo do Android para testar se existia, sobrecarregando a thread de I/O em listas grandes.

Solução Aplicada: A verificação foi otimizada para usar contentResolver.query(uri, arrayOf(OpenableColumns.DISPLAY_NAME), null, null, null), inspecionando apenas os metadados do cursor sem alocar nem ler streams de dados pesados.
