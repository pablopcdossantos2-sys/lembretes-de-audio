FALHA-01

ForegroundServiceStartNotAllowedException em Android 12+ (API 31+)

Crítica Background
📁 app/src/main/java/com/example/worker/AudioReminderWorker.kt:36 & BootAndAlarmReceiver.kt:43

O AudioReminderWorker e o BootAndAlarmReceiver chamam diretamente AudioReminderService.startOrRefresh(context), que executa context.startForegroundService(intent) enquanto a aplicação está em segundo plano. A partir do Android 12 (API 31), o sistema operacional proíbe explicitamente o início de Foreground Services a partir de segundo plano sem exceções formalmente qualificadas, lançando uma exceção fatal não tratada do tipo ForegroundServiceStartNotAllowedException.

Impacto Direto: Quando o WorkManager executa o worker periódico de checagem, a exceção é capturada no catch genérico, fazendo com que o WorkManager retorne Result.retry(). Isso gera um loop contínuo de tentativas repetidas em background, aquecendo o dispositivo e drenando a bateria do usuário.
✗ Código Atual Problemático
// AudioReminderWorker.kt
override suspend fun doWork(): Result {
    ...
    // Inicia Foreground Service de dentro do Worker em background
    AudioReminderService.startOrRefresh(context)
    return Result.success()
}
✓ Solução Recomendada
override suspend fun doWork(): Result {
    val prefs = prefsRepo.getPreferences()
    if (prefs.isAppMasterEnabled) {
        // Apenas reagenda o alarme exato diretamente sem acordar o FGS
        ScheduleCalculator.rescheduleDirectExactAlarm(context)
    }
    return Result.success()
}
FALHA-02

Finalização prematura do processo por falta de goAsync() no BroadcastReceiver

Crítica Confiabilidade
📁 app/src/main/java/com/example/receiver/BootAndAlarmReceiver.kt:68-100

Em BootAndAlarmReceiver.kt, ao receber eventos críticos do sistema como BOOT_COMPLETED, TIME_SET e TIMEZONE_CHANGED, o código dispara uma corrotina assíncrona desacoplada usando CoroutineScope(Dispatchers.IO).launch { ... }. No ciclo de vida do Android, assim que o método onReceive() síncrono retorna, o sistema considera o Receiver concluído e reduz drasticamente a prioridade do processo (movendo-o para cached/idle), podendo matá-lo instantaneamente antes que o Room ou o AlarmManager terminem de reagendar os lembretes.

Impacto Direto: Ao reiniciar o aparelho ou ao mudar de fuso horário, os alarmes programados podem ser silenciosamente cancelados ou nunca reagendados, quebrando a garantia central de entrega dos lembretes periódicos.
✗ Código Atual Problemático
override fun onReceive(context: Context, intent: Intent) {
    ...
    // O método onReceive termina imediatamente enquanto a corrotina ainda roda
    CoroutineScope(Dispatchers.IO).launch {
        database.ensureInitialDataSeeded(context)
        rescheduleDirectAlarm(context)
    }
}
✓ Solução Recomendada
override fun onReceive(context: Context, intent: Intent) {
    val pendingResult = goAsync()
    CoroutineScope(Dispatchers.IO).launch {
        try {
            database.ensureInitialDataSeeded(context)
            rescheduleDirectAlarm(context)
        } finally {
            pendingResult.finish() // Sinaliza conclusão segura ao OS
        }
    }
}
FALHA-03

Uso Irrestrito de USE_FULL_SCREEN_INTENT com Risco de Violação de Política

Crítica Play Store Policy
📁 app/src/main/AndroidManifest.xml:9 & ReminderNotificationHelper.kt:150

O app declara android.permission.USE_FULL_SCREEN_INTENT e chama setFullScreenIntent(openPendingIntent, true) a cada lembrete disparado. A partir do Android 14 (API 34), a política do Google Play proíbe terminantemente o uso irrestrito de USE_FULL_SCREEN_INTENT para aplicativos gerais que não sejam alarmes despertadores puros ou aplicativos de chamada (VoIP). Além disso, invocar full screen intent enquanto o usuário interage com o aparelho interrompe abruptamente tarefas em andamento.

Impacto Direto: Alto risco de rejeição em submissões para a Google Play Store e experiência invasiva ao usuário, que pode ter jogos, vídeos ou digitação repentinamente sobrepostos pela tela principal.
✗ Código Atual Problemático
// Força intent em tela cheia incondicionalmente
builder.setFullScreenIntent(openPendingIntent, true)
✓ Solução Recomendada
val isDeviceLocked = (context.getSystemService(Context.KEYGUARD_SERVICE) as KeyguardManager).isKeyguardLocked
if (isDeviceLocked) {
    builder.setFullScreenIntent(openPendingIntent, false)
} else {
    // Em uso ativo, exibe apenas Heads-Up banner não-intrusivo
    builder.setPriority(NotificationCompat.PRIORITY_HIGH)
}
FALHA-04

Omissão de Perfis Noturnos Pós-Meia-Noite em ScheduleCalculator.getNextNTriggers

Alta Algoritmo
📁 app/src/main/java/com/example/domain/scheduler/ScheduleCalculator.kt:343-346

No método getNextNTriggers, o algoritmo itera dia a dia. Para cada dia searchDate, ele verifica: if (!profile.daysOfWeek.contains(searchDate.dayOfWeek)) continue. Essa verificação ignora por completo a segunda metade dos perfis configurados para cruzar a meia-noite (crossesMidnight). Impacto Direto: Perfis de plantão, vigilância ou horários noturnos deixam de tocar nas primeiras horas da madrugada seguinte, gerando falha grave na rotina de agendamento.
✗ Código Atual Problemático
for (profile in enabledProfiles) {

    if (!profile.daysOfWeek.contains(searchDate.dayOfWeek)) {
        continue
    }
    ...
}
✓ Solução Recomendada
val yesterday = searchDate.dayOfWeek.minus(1)
val isFromToday = profile.daysOfWeek.contains(searchDate.dayOfWeek)
val isFromYesterdayOvernight = profile.crossesMidnight && profile.daysOfWeek.contains(yesterday)

if (!isFromToday && !isFromYesterdayOvernight) {

}
FALHA-05

Falha total de AudioTrimmerUtil em áudios importados via content://

Alta Tratamento de Áudio
📁 app/src/main/java/com/example/util/AudioTrimmerUtil.kt:458-466

Em AudioTrimmerUtil.resolveFileFromUri, a função foi implementada para retornar null para qualquer URI cujo esquema não seja file:// ou caminho bruto. Quando o usuário importa um áudio do aparelho via seletor de arquivos do sistema (SAF), a URI retornada é do tipo content://com.android.providers.media.... Ao tentar abrir a ferramenta de aparar ou cortar silêncio, a função trimAudio retorna false imediatamente.

Impacto Direto: O usuário não consegue aparar nem editar nenhum áudio importado de sua própria galeria/pastas do celular, ficando a funcionalidade restrita apenas a áudios gravados internamente.
✗ Código Atual Problemático
fun resolveFileFromUri(context: Context, uri: Uri): File? {
    return if (uri.scheme == null || uri.scheme == "file") {
        File(uri.path ?: uri.toString())
    } else {
        // Retorna null para todo content:// !
        null
    }
}
✓ Solução Recomendada
fun resolveFileFromUri(context: Context, uri: Uri): File? {
    if (uri.scheme == "content") {
        // Cria cópia temporária em cache para análise de stream
        val temp = File(context.cacheDir, "trim_cache_${System.currentTimeMillis()}.tmp")
        context.contentResolver.openInputStream(uri)?.use { inStream ->
            temp.outputStream().use { inStream.copyTo(it) }
        }
        return temp
    }
    return File(uri.path ?: uri.toString())
}

FALHA-08

I/O síncrono excessivo e sem debounce em AudioDiagnosticLogger

Média Performance
📁 app/src/main/java/com/example/util/AudioDiagnosticLogger.kt:120 & 272-296

A função chama persistLogsDebounced() a cada linha de log registrada.
